# Shared contract

Every implementation in this repository serves the same small orders API and passes the same scenarios. The languages differ in how they express the four patterns. They must not differ in observable behavior, because the point of the repository is a side-by-side comparison.

The Python implementation in [`python/`](../python) is the reference. When this document and the reference disagree, fix whichever one is wrong so they agree again.

## Domain

An order has these JSON fields. Names are camelCase on the wire in every language.

| Field           | Type                                   |
| --------------- | -------------------------------------- |
| `id`            | UUID, generated by the server          |
| `customerEmail` | string                                 |
| `items`         | array of `{ "sku": string, "quantity": integer }` |
| `status`        | `"pending"` or `"processed"`           |
| `createdAt`     | RFC 3339 timestamp in UTC with a `Z` suffix |
| `processedAt`   | RFC 3339 timestamp in UTC, or `null`   |

Orders live behind a key-value store interface with two operations, `get(key)` and `put(key, value)`. The default store is in memory. Tests substitute a store that fails on every call so they can simulate an outage or a bug.

## Endpoints

| Method | Path                         | Success                                            | Expected failures                        |
| ------ | ---------------------------- | -------------------------------------------------- | ---------------------------------------- |
| `POST` | `/orders`                    | `201` with the order, `status` `pending`, `processedAt` `null` | `400 VALIDATION_FAILED`                  |
| `GET`  | `/orders/{orderId}`          | `200` with the order                               | `400`, `404 ORDER_NOT_FOUND`             |
| `POST` | `/orders/{orderId}/process`  | `200` with the order, `status` `processed`, `processedAt` set | `400`, `404`, `409 ORDER_ALREADY_PROCESSED` |

Successful responses use `Content-Type: application/json`.

## Input validation

Validation happens at the HTTP boundary, before any service or store code runs. An invalid request never touches the store.

| Input                 | Rule                                                 |
| --------------------- | ---------------------------------------------------- |
| `customerEmail`       | Required. A syntactically valid email address.       |
| `items`               | Required. Between 1 and 50 entries.                  |
| `items[].sku`         | Required string, 1 to 64 characters.                 |
| `items[].quantity`    | Required integer, 1 to 100.                          |
| Unknown fields        | Rejected at the top level and inside each item.      |
| Body                  | Must be valid JSON.                                  |
| `orderId` path segment | Must parse as a UUID.                               |

Each validation failure is reported in `errors` with a `field` path. Paths are dot-joined with zero-based array indexes: `customerEmail`, `items`, `items.0.quantity`, `items.0.sku`, `orderId`. A body that is missing or is not valid JSON is reported with the field `body`. The `message` for each entry comes from the language's validation library and is not part of the contract.

## Error response format

Every error response, including an unknown route, uses [RFC 9457 problem details](https://www.rfc-editor.org/rfc/rfc9457) with `Content-Type: application/problem+json`.

```json
{
  "type": "about:blank",
  "title": "Not Found",
  "status": 404,
  "detail": "Order 0b9e5a4e-8f43-4f7e-9d0a-7f6d1c2b3a4f does not exist.",
  "code": "ORDER_NOT_FOUND",
  "instance": "/orders/0b9e5a4e-8f43-4f7e-9d0a-7f6d1c2b3a4f",
  "requestId": "req-123"
}
```

| Member      | Meaning                                                          |
| ----------- | ---------------------------------------------------------------- |
| `type`      | Always `about:blank`.                                            |
| `title`     | The standard reason phrase for `status`.                         |
| `status`    | The HTTP status code.                                            |
| `detail`    | A client-safe sentence. It never contains internal error text.   |
| `code`      | A stable machine-readable code from the table below.            |
| `instance`  | The request path.                                                |
| `requestId` | The request ID, so a client can quote it in a support ticket.    |
| `errors`    | Present only for `VALIDATION_FAILED`: a list of `{ "field", "message" }`. |

## Error codes

| `code`                     | Status | `detail`                                               | Logged at ERROR |
| -------------------------- | ------ | ------------------------------------------------------ | --------------- |
| `VALIDATION_FAILED`        | 400    | `The request is invalid.`                              | No              |
| `ROUTE_NOT_FOUND`          | 404    | `Not Found`                                            | No              |
| `ORDER_NOT_FOUND`          | 404    | `Order {orderId} does not exist.`                      | No              |
| `ORDER_ALREADY_PROCESSED`  | 409    | `Order {orderId} was already processed.`               | No              |
| `DEPENDENCY_UNAVAILABLE`   | 503    | `A required dependency is unavailable: order-store.`   | Yes             |
| `INTERNAL_ERROR`           | 500    | `An unexpected error occurred.`                        | Yes             |

## Request IDs

Each request gets an ID that appears in the `x-request-id` response header, in the problem body's `requestId`, and in every log record about that request.

The server accepts the caller's `x-request-id` header when it matches `^[A-Za-z0-9_=-]{1,255}$`. Otherwise, or when the header is absent, the server generates a UUID. A caller-supplied value is untrusted input, so the server bounds what it will write into its logs.

## Logging

Logs are structured JSON, one object per line.

A request that ends in a 5xx response produces exactly one record at ERROR level. That record contains `request_id`, `code`, `path`, and the original error, including its message and cause chain or stack. The error lives under whatever key is idiomatic for the logger (`exception`, `err`, `error`).

A request that ends in an expected outcome (any 4xx) produces no record at WARNING level or above.

## Failure classification

The four patterns come from one question: is this failure expected, invalid input, or exceptional?

| Kind                   | Example                              | Handling                                                                 | Response |
| ---------------------- | ------------------------------------ | ------------------------------------------------------------------------ | -------- |
| Invalid input          | Bad email, quantity 0, malformed JSON | Rejected at the boundary by validation. The service never sees it.       | 400      |
| Expected outcome       | Order not found, already processed   | Returned as a value (a `Result`, a tagged union, a sentinel error). Not logged. | 404, 409 |
| Dependency unavailable | Store refuses the connection or times out | The repository translates the driver error into a typed dependency error that keeps the original as its cause. The central handler logs it. | 503      |
| Unexpected             | Any other error, which means a bug   | Nothing catches it on the way up. The central handler logs the real error and returns a generic body. | 500      |

The repository recognizes only the store driver's connection and timeout failures. Every other error passes through it unchanged, with the same identity, so a bug is never relabeled as an outage.

## Scenarios

Each implementation mirrors these test files with the same scenario names, adapted to the language's naming style. A scenario that needs a failing store uses one whose error message contains a fake secret, `postgres://admin:hunter2@db-01:5432/orders`, and asserts that the secret never appears in the response.

### Pattern 1: validation (`pattern1_validation`)

| Scenario                                          | Expectation                                                                 |
| ------------------------------------------------- | --------------------------------------------------------------------------- |
| invalid order is rejected with 400 naming the field | Five cases: missing `customerEmail`, malformed `customerEmail`, empty `items`, quantity `0` (`items.0.quantity`), empty `sku` (`items.0.sku`). Each returns `400`, problem JSON, `VALIDATION_FAILED`, and the named field appears in `errors`. |
| invalid order never reaches the store             | After an invalid `POST /orders`, the store is empty.                        |
| unknown field is rejected                         | A body with an extra top-level field returns `400 VALIDATION_FAILED`.       |
| malformed JSON is a validation failure            | A body of `{not json` returns `400 VALIDATION_FAILED` with the field `body`. |
| malformed order id is rejected before lookup      | `GET /orders/not-a-uuid` returns `400` and `errors` names exactly `orderId`. |
| valid order is created                            | Returns `201`, echoes `customerEmail`, `status` is `pending`, `processedAt` is `null`. |

### Pattern 2: error hierarchy (`pattern2_error_hierarchy`)

| Scenario                                                 | Expectation                                                              |
| -------------------------------------------------------- | ------------------------------------------------------------------------ |
| dependency unavailable carries its status and code       | The dependency error is an application error with status `503`, code `DEPENDENCY_UNAVAILABLE`, and dependency `order-store`. |
| repository translates driver errors and keeps the cause  | For both a connection-refused and a timeout driver error, the repository returns or raises the dependency error, and the original driver error is reachable as its cause by identity. |
| repository lets unexpected errors through untouched      | A non-driver error from the store reaches the caller as the same error object, not wrapped as a dependency error. |

### Pattern 3: central handler (`pattern3_central_handler`)

| Scenario                                               | Expectation                                                              |
| ------------------------------------------------------ | ------------------------------------------------------------------------ |
| dependency outage returns 503 without leaking internals | Store refuses the connection. `GET /orders/{uuid}` with `x-request-id: req-503` returns `503`, problem JSON, `DEPENDENCY_UNAVAILABLE`, `requestId` `req-503`, and no secret in the body. Exactly one ERROR record, with `request_id` `req-503` and the error attached. |
| unexpected error returns generic 500 and logs the real one | Store fails with a generic error. Returns `500`, `INTERNAL_ERROR`, the generic `detail`, `requestId` `req-500`, and no secret in the body. Exactly one ERROR record, with `request_id` `req-500`, and the secret appears in the logged error. |
| request id is generated when the caller sends none     | The body's `requestId` is non-empty and matches the `x-request-id` response header. |
| untrusted request id is replaced                       | A caller-supplied `x-request-id: has space` is not echoed. A generated ID is used instead. |
| unknown route uses the same problem format             | `GET /nope` returns `404`, problem JSON, `ROUTE_NOT_FOUND`.               |

### Pattern 4: result values (`pattern4_result`)

| Scenario                                          | Expectation                                                                 |
| ------------------------------------------------- | --------------------------------------------------------------------------- |
| get unknown order returns not-found value         | Calling the service directly returns a not-found value carrying the order ID. No HTTP involved. |
| processing twice returns already-processed value  | The first `process` succeeds. The second returns an already-processed value carrying the order ID. |
| unknown order maps to 404                         | `GET /orders/{random uuid}` returns `404 ORDER_NOT_FOUND`.                  |
| already processed order maps to 409               | Processing an order twice over HTTP returns `409 ORDER_ALREADY_PROCESSED` the second time. |
| processing a pending order succeeds               | Returns `200` with `status` `processed`.                                    |
| expected outcomes are not logged as errors        | After a `409` and a `404`, there are no log records at WARNING or above.    |

### Antipattern: catch everything (`antipattern_catch_everything`)

This file makes the article's thesis executable.

| Scenario                                                        | Expectation                                                       |
| --------------------------------------------------------------- | ----------------------------------------------------------------- |
| swallowing makes an outage indistinguishable from a missing order | A helper that wraps `repository.find` in a catch-everything block returns the same empty result for a missing order on a healthy store and for any order on a store that refuses connections. Nothing is logged. |
| letting it propagate keeps the outage visible                   | Calling `repository.find` directly on the refusing store surfaces the dependency error. |

### Language-specific additions

Go and Rust have no exceptions, so an uncaught failure there is a panic. Those two implementations add one scenario to `pattern3_central_handler`: **a panic in a handler returns the generic 500 and is logged**, with the same body and logging expectations as the unexpected-error scenario.

An implementation that writes its own log formatter, as the Python one does, tests that formatter. An implementation that uses a logging library's JSON output does not need to.

## Out of scope

- `405 Method Not Allowed`. Some routers return it as plain text and cannot change that without workarounds that would obscure the example.
- Authentication, persistence beyond the in-memory store, pagination, and idempotency keys.
